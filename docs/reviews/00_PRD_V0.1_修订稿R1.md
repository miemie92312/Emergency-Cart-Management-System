# 抢救车管理助手 PRD V0.1 修订稿 R2

日期：2026-11-07。依据：原 PRD V0.1、源码审查及用户本轮产品评审。原始附件保持不变。

状态：定位冻结为“护士个人使用的轻量化抢救车管理工作台”。当前交付 Prototype，先验证五页任务流程，使用独立模拟原型，不改旧项目代码、不连接真实数据库。M0 的修复范围保留已有批准，暂不执行。

**最新交付策略：Prototype → 可运行 Demo → 经许可个人辅助试用 MVP，是同一产品逐步成熟。** Demo 优先复用原生项目，先修可靠性、定数据模型、跑最小闭环；Vue 3 + Vant 仅在动态配置或页面复杂度确实阻碍迭代后引入，不作为必须先完成的里程碑。旧文件名保留以免断链，内容以 R2 为准。

双重目标：实际辅助一位护士管理自己的车，以及积累有证据的 AI 辅助产品设计/开发案例。未完成开发、访谈、试用与效果不能提前写入简历。14 天只记为首轮验证冲刺计划；完成周期与成果按实际证据填写。

关联：[审查证据](./01_项目审查报告.md)、[数据契约](./02_数据模型与迁移设计.md)、[M0–M4 实施计划](./03_分阶段实施计划.md)。需求以本修订稿为当前依据，原 PRD 中冲突的范围和验收不再执行。

## 1. 产品目标与首轮验证

为护士个人提供本地记录工具，减少清单查找、效期识别、数量更新和检查留痕中的遗漏。是否降低工作量，需要真实操作验证；论文结果和演示数据不能作为本产品效果或医院配置的证明。

主要路径：**打开首页 → 选择抢救车 → 查看物品与异常 → 逐项确认或更新数量 → 保存记录。**

首先验证：使用者是否愿意录入并持续维护；录入负担是否低于原有纸质/Excel 流程；能否区分未知、异常与已确认；能否独立备份并恢复。少量形成性试用用于发现问题，不宣称具有统计代表性或取得临床收益。

本地个人模式是明确边界：无账号、后端、云同步、多人共享、临床建议或患者信息。个人记录不替代医院正式制度和记录。若用户真正需要多人共享，先重新验证产品定位，不自动扩大工程范围。

## 2. 首版范围及交付顺序

| 范围 | 要求 | 里程碑 |
|---|---|---|
| 旧版安全 | 事务完成再报成功；导入先校验、原子替换、失败不改原库；完整旧备份 | M0 |
| 检查可信边界 | 停止批量生成貌似逐项完成的记录；旧记录不补正常、不推断录入方式 | M0 起持续遵守 |
| 核心模型 | Cart、CartItem、ItemBatch、InspectionRecord、StockChangeRecord；校验与迁移演练 | M1，无完整业务 UI |
| 核心 Demo | 首页选车、多车详情/配置复制、四类物品、空白科室入口、效期与数量、单项检查、使用补充、完整 JSON | M2；优先原生实现 |
| 适量完善 | 四类基础扩展字段、Excel、备份界面、PWA 安装与离线；Excel 属 Demo 的 P1，PWA 属试用准备 | 按 Demo/MVP 需要完善 |
| 验证 | Android/iOS 实机与护士操作反馈，修改不合理交互 | M4 |

M2 是先供操作评估的最小 Demo，不把 M3 全部完成作为取得第一次反馈的前提。M2 可通过原浏览器 H5 入口评估；PWA 安装能力不作提前承诺。真实配置与医院场景使用仍须获得相应确认。

### 2.1 首版取消的核心要求

- **二维码不属于首版核心范围和发布门槛，不引入 qrcode.vue、扫码器、打印标签或二维码下载。**
- 保留车列表和独立详情页作为入口；车详情路由不依赖二维码，Vue Router 在 M2 多车页面引入。
- 后续如需二维码，先验证使用频率、是否返回原存储环境、是否实质要求多人共享，再单独决定，不沿用原 AC10 强制验收。
- 自定义字段仅文本、数字、日期、备注四类；不做单选、多选、开关、公式、字段联动、拖拽设计、脚本和远程字典。
- 不做复杂库存流转、采购、财务、审批、设备维修周期管理、后台准时提醒或通用低代码平台。

延后二维码是价值与成本的取舍，不是本地模式与二维码在技术上绝对冲突：同一存储环境仍可通过链接定位本地车，但不能据此实现跨设备共享；首版优先验证车列表入口是否已足够。

## 3. 首页、车与物品

首页优先展示车列表和异常：车数、在车物品记录数、过期/近效期/数量异常、日期规则待确认项、最近记录。本地数据说明和备份入口始终可见。没有医院检查周期规则时只显示最近检查时间、从未记录和本次进度，不计算“本班已完成/逾期”。

每车有独立 id、名称、科室、位置和物品清单。支持创建、编辑、复制配置。复制生成新车 ID，仅复制物品配置，不复制实际库存和检查历史；数量初始未知。归档不破坏历史，不以删除作为日常清空方式。

物品以 CartItem 表达在车实例，名称相同也不跨车共享库存。支持添加、编辑、搜索、按类型筛选和存放位置设置。公共字段：名称、规格、单位、应有数量、实际数量、位置、备注；不适用的字段不强制填写。

| 类型 | 固定业务组件 | 差异 |
|---|---|---|
| 药品 | MedicineFields | 批次与效期；不预填药品名、规格和数量 |
| 医用耗材 | ConsumableFields | 按适用性启用批次、效期 |
| 器械设备 | EquipmentFields | 型号、状态、用户确认的检查项目；不套药品效期规则 |
| 其他物品 | 其他物品固定字段区；若迁移 Vue 再用 CustomFields | 先提供公共字段，扩展字段按需要启用 |

新增一种药品只增加一条数据，不增加组件。字段配置只承担必要录入，不承担通用表单平台能力。

Demo 提供普通病区、急诊、ICU、儿科、手术室/麻醉恢复、妇产科、自定义科室的空入口。各科室差异尚未确认时只共用基础分类与字段，不按科室名虚构检查标准。没有经医院确认的物品、规格和数量，任何入口都不得自动填成真实清单。演示数据有持久标识和持续可见提示；旧数据用途未知时不能自动认证为正式配置。

## 4. 数量与批次规则

- 应有数量和实际数量分开；旧 minimumQuantity 只保留为旧最低库存阈值，应有量未知时为空。
- 首版仅支持支、瓶、件等离散计数物品；数量精度固定为 0，值为有限非负整数，不四舍五入导入的小数。
- 不把“规格包含 ml”当成实际数量采用毫升计量；规格文本和计数单位是两个字段。未来若支持升/毫升等连续计量，另行设计单位与小数精度，不在当前实现中预建通用计量引擎。
- 跟踪批次的物品，实际数量唯一来源为批次数量之和；CartItem 不再保存另一份可编辑总数。无批次的计数物品可保留单一聚合数量，不能两套数量同时写。
- 未盘点/未录入与已确认零数量分开。不能把未知视为零或正常，不能用应有数量初始化实际数量。
- 同物品可有多个批次，每批有独立数量与效期；同名记录和同批号记录不自动合并。
- 使用、补充和更正只做必要记录：前后数量、批次信息、原因和发生/录入时间。数量更新和记录同事务；补足数量不等于完成检查。
- 部分开启的批次可拆分数量，但开启后时限的自动推算及复杂规则不纳入首个 Demo；医院未确认的日期规则不得推断。

## 5. 日期精度与提醒

ItemBatch 增加 `expiryPrecision: 'day' | 'month'`，与有效期原值一起保存。字段可以整体未设置；已填写时值与精度必须匹配并通过运行时校验。

| 输入/情况 | 保存 | 展示与计算 |
|---|---|---|
| `2027-06-15` | 原值 + day | 按本地日历日期计算剩余天数 |
| `2027-06` | 原值 + month | 显示“日期规则待确认”；不补月末、不算倒计时 |
| 缺失效期 | 不填两字段 | 灰色“未设置” |
| 日期不存在/格式与精度不符 | 阻断保存/导入工作数据，列明错误 | 不修正成其他日期，不显示正常 |
| 不适用效期的设备等 | 明确不适用 | 不进入药品效期统计 |

日精度规则：剩余天数小于 0 为过期；0 至阈值含端点为近效期；大于阈值为正常。阈值可配置，默认 30 天仅为软件默认，不是临床标准。

首版年月精度统一保持待确认，不实现通用医院日期政策引擎。待确认项单独统计，不能混入正常、近效期或过期计数。前台切回和跨日刷新提醒，不依赖后台定时执行。

## 6. 检查真实性、时间与设备整体状态

每项初始未检查；使用者明确选择正常或异常，异常可同时包含数量不足、过期、包装异常、缺失、设备异常、其他，并填写必要备注。软件只能证明“保存了一项人工自报”，不能证明实际实物安全。

批量入口最多选择范围或填公共草稿，不能提交所有项目均已检查。M0 优先暂停原批量提交，无需先开发任务系统。未检查项目不能自动补成正常。旧记录保留人、时间、备注与原始数据，但结果和操作方式未知，不进入新版逐项确认数。

**首版不开放手工修改检查发生时间，也不开放历史补录入口。**

- 新记录 checkedAt 由设备在用户明确确认时生成，`timeSource='device'`。
- recordedAt 为本次系统写入记录的时间，事务完成后才展示已保存。不能据这两个设备时间字段声称具有可信外部授时能力。
- 旧记录的 timeSource 为 unknown，recordedAt 没有证据时为空，不能补成迁移时间。
- 以后若确实开放补录，需要 user_adjusted、原时间与修改原因等专门设计；本轮只保留概念边界，不实现补录 UI。

设备只有在**存在已确认的必检项目、所有必检项均完成且正常**时，才允许保存“设备整体正常”。必检项未填、异常或被填“不适用”都不能绕过。可先记录异常，但未完成的其余项目仍显示未完成；不能把异常登记当成整项检查完成。

检查记录保存当时名称、数量、批次、精度和设备项目快照；后续编辑不改写历史。更正通过追加关联记录完成。补充后显示待复核，显式再检查才成为已复核；数量再次改动后不沿用旧复核状态。

## 7. JSON、Excel 和 PWA

**JSON 可靠性是前置能力：** M0 修好旧版导出/恢复；M1 在新模型演练中先验证新版完整备份恢复；M2 开始写新数据前已有恢复路径；M3 只是完善界面和使用体验。

导入：识别格式与版本 → 完整校验 → 预览影响 → 提示另存恢复前备份 → 二次确认 → 单库事务替换 → 成功提交后刷新。任何校验或写入失败不改变原数据。旧 JSON 外层和裸数据两种格式均保留兼容，不删除旧库，不自动双写或合并数据集。

Excel 在 M3 使用 SheetJS CE 本地生成四个 Sheet：车信息、物品清单、批次效期、检查记录。年月效期原样导出，增加精度和“规则待确认”说明，剩余天数为空；旧检查结果未知，不能导出为正常。Excel 不作为完整恢复格式，首版不支持 Excel 导入。

PWA 在 M3 完善安装、离线资源和提示更新，M4 分别验证 Android/iOS。业务数据仅本机保存；不显示“未同步/已同步”，显示离线状态与最近备份文件生成时间。缓存版本升级不得清除数据库或自动刷新未保存表单。浏览器清理网站数据仍有丢失风险，持久存储申请不代替文件备份。

## 8. 技术引入顺序

| 阶段 | 技术与边界 |
|---|---|
| M0 | 原生 HTML/JS/IndexedDB；只做有必要的安全修复和验证，不搭 Vue 工程 |
| M1 | TypeScript 数据契约、Zod、业务/迁移测试、Dexie 隔离演练；不以完整 UI 为前提 |
| Demo | 优先原生模块化；复杂度确实阻碍迭代才引入 Vue 3/Vite/Vant。路由按实际实现选择，不因多车就强制框架迁移 |
| M3 | SheetJS CE、vite-plugin-pwa 按功能加入 |
| 暂缓 | Pinia；qrcode.vue 仅在二维码需求未来重新确认后考虑 |

每次引入库才核对实际锁定版本、完整性、转依赖和 LICENSE/NOTICE。既有候选许可证检查不等于未来安装树已通过。优先复用成熟库，不复制授权不明或不适合当前边界的库存系统。

## 10. 待验证事项与当前批准边界

尚需验证：个人工具是否符合真实交接方式、个人设备使用限制、应有量及日期规则确认责任、设备必检项来源、录入负担、备份保存位置和恢复难度。无需为记录这些问题新增复杂管理文档，在试用记录中持续更新即可。

用户已批准 M0，未批准立即执行全量迁移。当前先完成独立低保真原型和流程评审，旧项目开发仍未启动；后续 M0 不需重复申请已给出的范围授权，但不得扩大为新模型投产或 Vue 全面迁移。原型与操作任务见[原型交付说明](../../原型/抢救车管理助手_低保真/流程与评审说明.md)。
