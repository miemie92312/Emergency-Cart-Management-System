## 1. 结论与实施建议

**可以增量升级；不建议直接重写，也不建议把完整技术栈迁移作为第一步。** 现有项目是可以读懂并继续维护的单文件 Demo，已经具备药品录入、效期计算、库存提醒、检查历史和 JSON 备份基础。真正的阻碍是记录语义和写入可靠性，而不是缺少 Vue。

建议顺序：

1. 固定旧版本、建立回归证据，先解决导入恢复、事务完成判断和批量检查语义。
2. M1 先验证核心数据契约、业务逻辑、旧库/旧 JSON 迁移和新版完整恢复，不做完整 UI。
3. 先复用原生代码形成多车、批次、逐项检查和补充的核心 Demo；只有复杂度实际阻碍迭代时才逐步替换为 Vue。
4. M3 按需完善空模板、四类基础字段、Excel 与 PWA；M4 收口实机和用户验证。二维码延后单独验证，不纳入首版。

采用 Vue 3 + TypeScript + Vite + Vant + Dexie 是对完整 PRD 的合理选择，但并非 H5、离线或二维码的技术前提。若目标仍只是单车药品 Demo，继续模块化原生 JS 成本更低。是否采用全量 PRD，应先通过目标用户验证。

**上线试用前优先阻断的四类风险：**

- 恢复失败可能已经删除旧数据。
- 批量点击生成的历史与单项记录不可区分，且没有检查结果字段。
- “最低库存”被误当作“医院要求的应有数量”。
- 更换域名、浏览器或扫码入口后读不到本地数据，被误认为数据丢失或二维码共享失效。

本次审查及 R1 修订只处理文档。未修改远程仓库、未创建提交或 PR、未安装项目依赖、未接触任何真实医院本地数据。

### 3.2 当前技术和职责

| 部分 | 实际实现 | 判断 |
|---|---|---|
| 页面 | 原生 HTML、CSS 媒体查询，移动端竖屏布局 | 可复用信息结构和视觉变量，不应逐字搬运全部 DOM |

| PWA | manifest + 手写 SW | 有缓存基础，不能据此宣称移动端安装与离线验收通过 |
| 第三方运行依赖 | 源码未引用外部运行库/CDN 脚本 | 当前不存在可执行的 npm 依赖审计对象 |

### 3.4 当前存储契约

数据库为 `RescueCartDB`，原生版本 `1`。[建库代码](https://github.com/miemie92312/Emergency-Cart-Management-System/blob/a25bb82ad4ae4342bc8e9972554695480b184137/index.html#L213-L288)

| Store | 主键/索引 | 已使用字段 |
|---|---|---|
| drugs | `keyPath: id`，无额外索引 | id、name、specification、quantity、minimumQuantity、batchNumber、expiryDate、location、remark、createdAt、updatedAt |
| checks | `keyPath: id`；索引 drugId、checkedAt | id、drugId、checker、remark、checkedAt |
| settings | `keyPath: key` | `{ key, value }`；内存默认 warningDays=30、lastChecker="" |

每条 drug 同时承担物品定义、当前数量、单个批号和效期；没有 cartId、单位、应有数量、类型和多批次关系。checks 不含 result、batchId、操作来源、被检查内容快照。

备份外层为 `{ version: "1.0", exportTime, data: { drugs, checks, settings } }`。其中 settings 是普通对象，不是数据库中的 `{key,value}[]`。导入也接受裸 `{drugs,checks,settings}`。这两种形态都必须兼容。[导入导出源码](https://github.com/miemie92312/Emergency-Cart-Management-System/blob/a25bb82ad4ae4342bc8e9972554695480b184137/index.html#L449-L479)

## 5. 重点缺陷及优先级

P0：新试用/迁移前必须处理；P1：核心业务阶段处理；P2：发布与体验阶段处理。这是本次产品风险排序，不是已确认的线上事故等级。

| 编号 | 优先级 | 问题、证据与影响 | 建议 |
|---|---|---|---|
| F01 | P0 | importData 只判断两个数组便清空旧记录，之后逐条 put；中途缺主键等异常会留下半恢复状态，catch 仍统一称“格式不正确”。index.html 463—477 | 全量运行时校验、恢复预览、原子事务、恢复前快照；错误区分校验/配额/写入失败 |
| F02 | P0 | saveCheck 为全部筛选结果写同一人/时间/备注，未记录 result 和来源；旧单项与批量记录结构完全相同。422—435、499 | 批量只创建待检清单/填充草稿；逐项明确确认才保存；旧数据统一标记历史来源不明 |
| F03 | P0 | requestStore 在 request.onsuccess resolve，未等 transaction.oncomplete；请求成功后事务仍可能失败。275—283 | Promise 以事务完成为成功，处理 abort/error；多表操作共用事务；UI 在提交后更新。[IndexedDB 规范](https://www.w3.org/TR/IndexedDB-3/#dom-idbtransaction-oncomplete) |
| F04 | P0 | drugCard 的三个 data-id 直接插入 drug.id，导入又不校验 id；常规文本有 escapeHtml，但 ID 属性没有。354、467 | 校验主键、拒绝危险导入；在旧版转义属性；Vue 用属性绑定并禁止不必要的 v-html。确认的是属性注入路径，未做浏览器脚本执行验证 |
| F05 | P1 | 缺有效期返回 key=normal，显示“未设置”却沿用绿色样式。245—250 | 区分 normal/warning/expired/unset/notApplicable/invalid；不得用绿色掩盖未知 |

| F07 | P1 | minimumQuantity 默认 3，是软件最低库存提醒，不是医院基数；没有 requiredQuantity。183、253、396—397 | 分开保存旧阈值与新应有数量；迁入的应有数量保持未确认 |

## 6. 技术迁移必要性与增量路径

| 选择 | 必要性判断 | 收益 | 新成本/边界 |
|---|---|---|---|
| 原生 JS 先模块化 | 必须保留为可选路径 | 最快修可靠性、便于回归，零框架迁移风险 | 类型/字段/页面继续增长后模板分支和状态同步成本变高 |
| TypeScript + Vite | 完整 PRD 下建议尽早引入 | 模型契约、模块边界、构建/测试入口 | TS 不校验导入 JSON；增加 Node 工具链和构建发布步骤 |
| Vue 3 | 完整 PRD 下建议 | 多页表单和配置驱动渲染可维护，复用 UI | 迁移期并存与回归成本；不能一次替换全部页面 |
| Vant 4 | 建议 | 复用手机表单、弹窗、日期选择、列表反馈 | 按需引用、主题统一；只用一套完整 UI 库 |
| Dexie | 建议，但不是数据库更换 | 事务、查询、版本管理较清晰 | 原生库版本与 Dexie 版本不是同一编号；需专门迁移和错误测试 |
| Vue Router | 多车页面时建议 | 稳定深链接与返回行为 | hash/history 取决于静态托管，不得先写死根域名路径 |
| Pinia | 暂缓 | 日后存在多个独立跨页工作流时可加入 | 当前可先用 composable + repository；避免再复制全库为第二真源 |
| vite-plugin-pwa | Vite 稳定后引入 | 资源修订、离线外壳、更新提示 | 旧 SW 仍需专门交接；懒加载模块离线可达性需验证 |

推荐先新增 `src/domain/`、`src/data/legacy/` 等边界，原页面通过适配器调用可靠存储；再通过有限挂载点替换卡片和表单；最后切换页面壳与路由。Vue 与旧 DOM 不应同时修改同一节点。旧文件和历史提交保留，数据库不做破坏性重建。详细步骤见实施计划。

## 7. PWA、二维码和 Excel 方案审查

### 7.1 PWA

当前 manifest 的 `icons: []` 和基础 SW 不足以证明安装合格。计划补齐 192/512 图标、maskable 图标、Apple touch icon、明确 id/start_url/scope。主业务外壳、路由页面与需要离线使用的导出代码均应纳入离线资源策略。

使用 vite-plugin-pwa 的提示更新模式；检查、编辑、导入进行中不自动刷新。官方也指出自动重载可能丢失正在填的表单，并建议表单应用采用提示更新。[自动更新说明](https://vite-pwa-org.netlify.app/guide/auto-update)、[提示更新说明](https://vite-pwa-org.netlify.app/guide/prompt-for-update)

旧 `sw.js` 注册 URL 的交接必须先解决：测试部署桥接 SW 或保持同一注册 URL 的替换路径，确保旧缓存优先逻辑不再阻挡新入口；仅清除本项目已知旧缓存名，不删除整个 origin 的缓存。预缓存业务资源与版本清理优先复用 Workbox。[Workbox 官方文档](https://developer.chrome.com/docs/workbox/modules/workbox-precaching)

本地数据不会自动上传；AC14 的“未同步状态”应改为“离线可用 / 数据仅在本机 / 最近备份时间”，否则暗示存在未来自动同步。首次离线且未缓存、容量不足、清除网站数据、私密浏览都需有明确行为。可检测并请求持久存储，但不得宣称浏览器永不清理。[WebKit 存储政策](https://webkit.org/blog/14403/updates-to-storage-policy/)

### 7.2 原方案二维码评估（R1 已移出首版）

以下保留为原方案的取舍依据，不列入 M0–M4 任务；不为它引入依赖、扫码器、下载或打印界面。首版从首页车列表进入独立详情。

- 仅编码稳定 URL 与 cartId，不编码库存明细、不修改数据、不证明检查完成。
- `qrcode.vue` 支持 canvas 和 SVG，足够生成、PNG/SVG 下载；打印用浏览器打印样式与预览，无需额外二维码服务。[组件官方说明](https://github.com/scopewu/qrcode.vue)
- 不默认做应用内扫码器：先使用手机系统扫码入口，避免相机权限与额外扫码库。若“同一台手机必须始终回到原 PWA 存储环境”成为硬需求，再验证应用内扫码是否必要。
- 关键失败路径是“车 ID 存在于 URL，但当前浏览器没有该车”。页面应说明本地模式，提供导入备份、返回车列表；不能静默创建同名车或从演示库补数据。
- 普通静态托管优先 `/<base>/#/cart/:cartId`。若必须采用 PRD 的 `/<base>/cart/:cartId`，托管需支持 history fallback，且验证首次直达、刷新和离线导航。GitHub Pages 项目地址还需要正确设置 Vite base。[Vite 官方部署文档](https://vite.dev/guide/static-deploy.html#github-pages)
- “重新生成”默认只重绘相同 cartId 的标签；不是更换 ID。域名变化会使纸质二维码失效，部署地址应先确定。
- “同一设备”不是充分条件：浏览器、用户配置、origin、存储分区和系统扫码打开的环境都影响读取。Safari、桌面 PWA、内置浏览器是否共享本地数据必须实测，不能做统一保证。[IndexedDB 存储隔离规范](https://www.w3.org/TR/IndexedDB-3/#database-api)

### 7.3 Excel

采用 SheetJS CE，在本地生成真正 `.xlsx`，保留四个 Sheet：车信息、物品清单、批次效期、检查记录。列中保留稳定 ID、导出时间、数据用途/来源、检查可信标记。应有数量未确认时留空并注明，旧检查结果未知时不得导出为正常。

批号、ID、规格作为字符串单元格；数量作为数值；日期优先输出明确的 YYYY-MM-DD 文本，避免读表软件时区误解。用户文本如以 `=`、`+` 等开头，也必须保持字符串，不生成公式字段；剩余天数导出计算值而不是套用论文公式。需要与 Excel/WPS/LibreOffice 对照验证。

SheetJS 官方分发站为 cdn.sheetjs.com，安装时按官方框架文档固定 tarball 版本并锁定完整性；不要假设 npm 上任意 `xlsx` 包就是官方当前推荐版本。构建打包进应用，不能依赖运行时外网 CDN。[分发说明](https://docs.sheetjs.com/docs/getting-started/installation/)、[框架安装](https://docs.sheetjs.com/docs/getting-started/installation/frameworks/)

大数据导出先测手机内存和主线程阻塞，再决定是否使用 Web Worker；不预先加入后台服务。Excel 不是完整恢复格式，V0.1 不接入 Excel 导入。

## 9. PRD 的缺失、冲突与过度设计

| 问题 | 为什么需要调整 | 建议/待验证 |
|---|---|---|
| 缺少 CartItem | ItemBatch.itemId 无实际归属；一个模板不能同时代表多台车的在车物品 | 增加 CartItem；模板定义、在车配置、批次分开 |
| 最低库存与应有数量混同 | 旧 threshold 不是医院要求；迁移会虚构临床配置 | requiredQuantity 未确认保持空；保留旧最低库存提醒 |
| 模板两层含义混用 | 科室模板与单个物品模板是不同对象 | DepartmentTemplate 引用 ItemTemplate；复制为快照，不自动改在用车 |
| 四种物品 + 全类型自定义字段全部首发 | 配置编辑器、规则维护、数据迁移和用户理解成本可能超过日常清点收益 | 先内置字段和必要额外字段；完整 V0.1 可分阶段做完，拖拽/公式/跨字段规则留后续 |
| 多个空白科室模板 | 相同空内容可能只有名称不同，不能证明模板价值 | 保留空入口承诺，先验证是否只需科室下拉与复制车配置 |
| 单一检查结果字符串 | 同物品可同时短缺、过期、包装异常；设备还有项目状态 | 结果 normal/abnormal + 多个 findings；不能只用一个枚举覆盖多个事实 |
| 只检查“是否点过” | 无法证明实物检查，旧同时间记录也不能反推批量 | 新录入保存明确操作来源和人工确认；软件只能证明自报记录 |
| “待检查”没有规则 | 未定义每班/每天/封条完整免开封等制度，无法算逾期 | V0.1 先显示“从未记录/最近记录时间”；检查周期由医院确认，不擅自按每日生成任务 |
| 补充完成与重新检查 | 补足数量不是包装/效期/设备都已核对 | 区分已更新、待复核、已复核；不得自动生成正常检查 |
| 设备用药品效期规则 | 维护周期/通电/功能状态不是药品到期日 | 明确 notApplicable，设备使用独立 checklist；维护周期后续 |
| 开启后有效期 | 同批次部分开启时，一条 openedAt 不够；规则依赖实际制度 | 首发可人工录入医院确认的日期；部分开启拆分数量分组，不自动推算临床时限 |
| QR 是核心入口但本地模式 | 班组共同扫码的实际需求可能与个人工具定位冲突；同机扫码也可能换浏览器 | 优先访谈/演练访问环境，保留车列表入口；不因此擅自增加后端 |
| AC14“未同步” | 产品没有同步通道，文案与架构矛盾 | 改为本机存储/离线/最近备份说明 |
| “常用操作不超过3步” | 未定义从哪个起点开始，表单输入与每项确认不能被无意义合并 | 定义进入清单、开始检查、录入后保存三个具体任务；分别测点击数、录入量、耗时 |
| 统计数量口径 | 物品种类、实物件数、批次数、异常物品数会相差很大 | 首页显示“在车物品记录数”；同物品多坏批次只计一次异常物品，明细再列批次 |
| 本地记录的可追责性 | 检查人只是自由输入姓名、设备时间可修改，JSON 也可编辑 | 明确自报辅助记录；不做电子签名/身份认证合规承诺，不增加登录 |
| 删除/复制语义 | 复制若连带现存数量、旧检查，会制造另一台车已配齐已检查的假象 | 默认仅复制配置；库存未知、检查为空；归档不破坏历史 |

### 9.1 论文依据的适用范围

论文确实支持清单、Excel 效期颜色提醒、二维码、使用后补充和人工核对的方向。它的实施同时包含组织培训、专人管理和督导；不是单独验证一个个人离线 App 的效果。论文报告的流程指标不能转为本产品承诺，也未直接验证患者结局。原文表 1 的新方法分组数合计与标注 n 不一致，均值差与所述缩短值也存在舍入/报告差异，引用时应注明“原文报告”，不要自行包装为精确收益。[论文全文](https://pdf.hanspub.org/ns_2251787.pdf)

论文表格中的 DATEDIF 示例也不应直接复制为本产品对所有过期日期的处理规则。PRD 允许软件默认 30 天是设计决策，不是已验证的统一临床阈值。

### 9.2 业务验证建议

建议在开发核心扩展前，邀请少量不同工作环境的目标使用者完成一台车的建档、一次异常检查、一次使用后补充及恢复备份演练。先使用合成数据，临床配置只由获得授权的使用者提供和确认。

记录：当前纸质/Excel 流程、手机与扫码入口、是否允许个人设备、谁拥有配置、应有数量来源、检查粒度、复核责任、备份可存放位置。比较录入负担、误操作、遗漏、恢复是否独立完成及用户反馈；不能只统计按钮点击后的“完成率”。样本规模与成功阈值由试用目标确定，不预先声称具有统计代表性。

## 10. R1 决策与当前停点

用户已批准 M0 原生数据安全修复；未批准立即全面迁移或开发全部功能。最新顺序为先独立 Prototype，再原生安全修复、数据与测试、核心 Demo、个人试用 MVP；Vue 按实际复杂度决定，不再以十个阶段管理。

首版取消二维码门槛；自定义字段限文本、数字、日期、备注；补充效期精度与离散数量限制；新检查时间由设备生成且不可手改，旧时间来源未知；设备必检项目未全部完成且正常，不能整体正常。具体需求与验收已写入 PRD R1。

医院规则、真实配置确认人和目标使用环境仍属待验证业务信息，不因文档或 M0 批准而视为已确认。本轮按用户最后“暂时不改代码”的指示完成文档修订后停下；后续启动 M0 无需重复索取同一范围授权，不自动延伸到 M1–M4 或发布。
