# 产品案例：抢救车管理助手

## 问题来源与目标

项目由一个原生 HTML/JS 药品巡检 Demo 增量演进。背景来自《信息化在规范抢救车管理中的应用》和对现有代码的审查，而非已完成的护士访谈。清单录入、效期查找、数量变更与检查留痕是待目标使用者验证的工作场景。

目标用户是一位护士或个人管理人员，产品是本地辅助工作台，不是医院级 SaaS。双重目标是交付可操作工具，以及形成有过程证据的产品设计与 AI 辅助开发案例。

## 从需求到交互

五个核心页面分别对应任务：工作台判断异常；车内清单查找；物品详情看批次与历史；检查页逐项确认；配置中心管理模板、规则和备份。建车、录入、批次和恢复确认采用弹窗，底部仅保留工作台、清单、配置。

- 建车与添加物品：空白入口，不预填临床名称、规格和数量；必要字段优先，可选字段展开。
- 查找效期：工作台异常直达已筛选清单，再看具体批次，避免只展示统计报表。
- 检查：每项明确选择，允许多异常，跳过仍未检查；设备必检未全正常不能整体正常。
- 补充：保存前后数量，显示待复核，不将补足库存自动变成检查正常。
- 恢复：先校验、预览和提醒备份，再确认覆盖，失败保持原数据。

[可点击低保真原型（下载 HTML 后打开）](../public/prototype/index.html)只用内存模拟；它不访问真实数据库。正式工作 Demo 与原型分开。

## 关键取舍

| 决策 | 理由 | 成本与后续验证 |
|---|---|---|
| 先修旧数据，再做功能 | 原 Demo 的恢复先删除后写入、请求成功当作事务完成、批量登记与未校验 ID 比框架更急迫 | 单独保留安全补丁和旧版只读入口；仍需真机验证 |
| 不立即迁 Vue | 五页与有限字段可由原生模块完成；构建工具只承担依赖打包、测试和 PWA | 组件规模变大时再评估，不把技术栈数量当成果 |
| 区分车、在车物品与批次 | 同一名称在不同车上拥有独立配置与数量；批次模式库存仅由批次汇总 | 模型稍复杂，但避免总数与批次数量两处修改 |
| 旧最低库存不填应有量 | 软件阈值不等于医院配置标准 | 迁入后应有量待确认，旧提醒独立保留 |
| 年月效期不补月末 | 没有确认日期政策，不能自行制定规则 | 暂不倒计时，显示日期规则待确认 |
| 暂缓二维码与云同步 | 本地二维码不能共享别人的 IndexedDB，实际访问入口尚未验证 | 降低成本，但不支持多人共享；不能暗示已同步 |
| 自定义仅四类字段 | 覆盖简单录入，避免低代码平台建设 | 不做公式、联动、多选或拖拽；验证是否需要扩展 |
| 演示与个人配置分开 | 演示清单不是临床标准，模拟检查不是真实检查证据 | 用途标记持续可见，导出同样保留来源 |

## 证据与当前限制

已完成：源码审查、范围收敛、五页交互原型、可运行工作 Demo、自动化回归及合成数据浏览器走查。数据库、JSON、XLSX 和生产 PWA 构建是实际实现，不是占位按钮。

尚未完成：护士访谈、经医院许可的真实辅助试用、Android/iOS 真机安装与系统离线验证，以及相对原流程的耗时/成功率效果评估。不能称为已经验证实用价值的 MVP，也不能把研发走查写成用户测试。

## 下一轮验证

一位参与者先做三项任务：建车并添加合成物品、找到近效期批次、完成一项检查并查看结果。评审者不提前指路；记录独立完成数、耗时、错填、遗漏、求助与原话。少量测试报告实际分子/分母，不将“90% 内部目标”写成已取得的总体成功率。

真实试用只能按获得的医院许可作为辅助流程并行；本轮仅模拟未来可能的替代流程，实际替代正式记录另行确认。论文报告结果不能直接当作本产品收益。

## AI 协作与个人贡献的表达

本案例包含需求与范围决策、模型和流程取舍、对 AI 产出审查、测试门槛与证据整理，以及 AI 辅助实现。代码由 AI 协作产出，不应包装成没有辅助的全部手写经历；对方案的选择、复核和取舍应以可解释的实际参与为准。

简历可据实写已交付的原型、业务闭环、数据可靠性与导出能力；未发生的访谈、真实效果及“实际开发历时 14 天”不能写成成果。[14 天范围对照](./delivery-14-day.md)用于组织交付材料，实际时间以 Git 提交为准。
